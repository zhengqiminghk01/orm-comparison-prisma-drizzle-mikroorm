测试日期：2026-10-12（UTC+8）。测试环境：一台 Linux 测试机；PostgreSQL 17.11 primary + streaming replica；Node v24.13.0。命令、版本和原始输出在本报告的 raw/ 目录。

结论

推荐：Prisma 7。版本必须锁定到精确的 7.x 版本。

运行时性能和体积：Drizzle 最好。ORM 自身开销：Drizzle 每次查询比 Prisma 快约 1.6–2.2 倍。打包体积（gzip）：Drizzle 约为 Prisma 的 1/20。冷启动：Drizzle 约为 Prisma 的 1/3。

需求 §5 的三项要求是读写分离、cursor 分页、事务内检查。三个 ORM 都满足这三项要求（已验证，见 §3.1 和 §5）。

推荐 Prisma 的 3 个原因：

  1. Maintenance cost 最低。team 的现有项目 ASJ 和 MCPB 都用 Prisma。两个仓库都用 Prisma 7 要求的 prisma-client generator。team 的 nestjs-practices skill 按 Prisma 编写。
  2. 无人值守时，migration 最安全。CI 和 AI agent 都属于无人值守场景。Prisma 拒绝执行会丢数据的 rename，exit code 为 1。Prisma 的 drift 检测返回可用的 exit code。Drizzle 和 MikroORM 的破坏性命令直接删除了数据（见 §3.2）。
  3. 性能差距不是本服务的瓶颈。ORM 之间的差距是亚毫秒级：主键查询 p50，Prisma 0.195 ms，Drizzle 0.111 ms。重 SQL 查询三者都是 47–50 ms。SQL 写法的影响更大：cursor 条件写法不同，查询耗时为 29.7 ms 或 0.077 ms（见 §3.3）。

可以改选 Drizzle 的条件：团队优先考虑内存和冷启动时，可以选 Drizzle。团队需要 row-value 比较或原生 bulk upsert 时，也可以选 Drizzle。选 Drizzle 时，团队必须接受以下三点：

  • Drizzle 仍是 0.x 版本，1.0 是 rc。Drizzle 0.45.4 的类型检查时间随 schema 变大而增长：200 张表时 Check time 为 3.39 s，1.0.0-rc.4 为 0.74 s（见 §2.4）。
  • rename 类 migration 必须在交互式终端（TTY）中人工选择。
  • drizzle-kit 不生成 down migration。

不推荐 MikroORM。原因：三者中最慢；本次测试出现 migration 生成错误（见 §4）；npm 下载量最低。

术语

  • ORM 自身开销：同一条简单 SQL 在 ORM 内的额外耗时。本报告用主键查询 1 行的耗时表示。
  • 无人值守：没有人在终端前确认的执行环境，例如 CI 和 AI agent。
  • drift：数据库实际 schema 与 ORM schema 定义不一致。
  • index churn：没有 schema 变化时，生成的 migration 仍然删除并重建索引。

3.3 性能

详细数据见 §5。

  • ORM 自身开销（主键查询 p50）：Drizzle 0.111 ms；Prisma 0.195 ms；MikroORM 0.405 ms。
  • 10 并发分页吞吐：Drizzle 5,126 次/秒；Prisma 4,146 次/秒；MikroORM 1,023 次/秒。MikroORM 的 p50 是 8.9 ms。
  • 冷启动（打包后，进程启动到第一条结果，中位数）：Drizzle 66 ms；Prisma 195 ms；MikroORM 325 ms。
  • benchmark 结束时的 RSS：Drizzle 约 201 MB；Prisma 约 346 MB；MikroORM 约 348 MB。
  • 打包体积（gzip）：Drizzle 77 KB；MikroORM 421 KB；Prisma 1753 KB。Prisma 未压缩为 4.99 MB，包含 query compiler wasm。
  • 重 SQL 查询（约 20 万行 group by）：三者都是 47–50 ms。这个场景的瓶颈是数据库。

cursor 查询不得只用 OR 条件，必须加冗余的 created_at <= c 条件或用 row-value 比较。只用 OR 条件时，查询耗时 29.7 ms。这个结论与 ORM 选择无关。

  • 只用 created_at < c OR (created_at = c AND id < i)：Index Cond 只有 tenant 和 parent；Filter 删除 98,798 行；耗时 29.7 ms。
  • row-value (created_at, id) < (c, i)：耗时 0.154 ms。
  • OR 条件 + 冗余 created_at <= c：耗时 0.077 ms。
三个 ORM 的 query API 都可以写冗余条件。本报告的 benchmark 都用「OR + 冗余条件」写法。来源：raw/10-explain.txt（单次 EXPLAIN ANALYZE）。

6. 局限

  • primary 和 replica 在同一台机器，没有网络延迟。网络延迟对 ORM 差距占比的影响：未验证。
  • 测试期间机器上有其他进程，可用内存约 2 GB。3 轮之间有波动，例如 MikroORM 10 并发分页 p50 为 7.8–10.6 ms。每个场景只运行 3 轮，没有做显著性检验。
  • 轮次之间的 VACUUM ANALYZE 没有执行：命令写法导致 PostgreSQL 报 "VACUUM cannot run inside a transaction block"。插入测试写入另一个 resource，不写入分页使用的热门 resource。comments 表每轮增加约 3.9 万行（3 个 ORM × 13,000 行）。
  • 测试的版本：Prisma 7.10、Drizzle 0.45.4、MikroORM 7.2.5。没有测试 Prisma 6.x、Prisma 8 rc。Drizzle 1.0 rc 只测试了类型检查（§2.4），没有测试运行时。
  • 只测试了 PostgreSQL。team 现有仓库使用 MySQL。
  • 测试代码按各 ORM 的常用写法编写，不一定是最优写法。MikroORM 每次请求使用 em.fork()，并有 3 处 as any。这两点对 MikroORM 结果的影响：未确认。
  • 开发效率和 AI 生成代码的质量：没有量化。代码行数只是粗略指标。
  • 安装耗时：没有可靠数据，本报告不列出。node_modules 大小包含 NestJS 和 CLI，不代表生产镜像大小。
  • M4 的 Prisma migration 目录是手写的。目录名时间戳用了 UTC+8，其他目录用 UTC，所以在新数据库上重放时顺序与创建顺序不同。该问题不影响本次结果。手写 migration 时，必须统一使用 UTC 时间戳。

7. 社区观点（节选）

  • Joseph Pire，Drizzle vs Prisma in production: 12 months later（2026-06）："prisma migrate dev is still the best migration tool I've used: shadow database, drift detection, clean history." 作者的新项目选择 Drizzle，理由是 "no codegen step… the SQL hitting the database is the SQL you read in the code."
  • drizzle-orm issue #5307（状态：open）：一位用户写道 "db:generate blocks the agent on a TTY prompt, the agent has to escalate to the human"。2026-10-10 的评论写道 "still hasn't been fixed even in v1 rc"。
  • Prisma CLI 文档：CLI 可以识别 AI coding agent 的调用；agent 执行破坏性操作时，文档给出的例子是 prisma migrate reset --force。
  • MikroORM 文档：默认情况下 "all of them will be wrapped in one master transaction"。这一点与 M5 拆分后仍然失败的结果一致。
  • PostgreSQL 17 文档："If ALTER TYPE ... ADD VALUE ... is executed inside a transaction block, the new value cannot be used until after the transaction has been committed."
